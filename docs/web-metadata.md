# Webサイトのメタ情報と検索公開

WebサイトやWebアプリを作るとき、公開範囲や共有方法に応じて、検索・リンク共有・ブラウザー向けの情報を確認する。
以下は共通の判断と確認項目であり、すべてのファイルや設定を全サイトに追加するという意味ではない。
各プロジェクトの実装・公開先・既存のURLを先に調べ、採否とその理由は必要に応じて各プロジェクトに残す。

## 先に決めること

- ページやデータを、誰が閲覧でき、誰に検索・共有してほしいかを分けて決める。公開案内と認証後の内容、検索結果、
  プレビュー環境が混在する場合も、それぞれ確認する。
- 既存の検索掲載・クロール・共有の設定を統一のためだけに変えない。正規ドメイン、既存の転送・別名、
  静的生成や配信サービスのrewrite、動的ページが返す初期HTMLとヘッダーも確認する。
- `robots.txt`、`noindex`、サイトマップからの除外は、情報へのアクセス制御ではない。非公開データは
  サーバー・API・ストレージの認証と認可で守り、公開HTMLや画像、メタ情報にも含めない。

## 確認する項目

| 項目 | 目的と判断 |
| --- | --- |
| `title`・`description` | タブや検索結果でページを説明する。公開ページごとの内容に合う文を用意し、個人情報や非公開の内容を含めない。検索結果でそのまま採用されるとは限らない |
| 言語・文字コード・viewport | HTMLの `lang`、文字コード、モバイル向けviewportを内容と配信に合わせる。利用者による拡大操作は制限しない |
| `robots.txt` | クロールを制御する必要がある場合、各オリジンのルートに配置する。検索掲載の禁止や秘密の保護には使えない。サイトマップを案内する場合は実際のURLと合わせる |
| robots meta・`X-Robots-Tag` | 検索結果へ載せないHTMLには `noindex` を検討する。PDF等の非HTMLにも必要ならHTTPヘッダーを使う。検索エンジンが指示を読める条件を下記で確認する |
| `canonical` | 同じ内容の別URLがある場合の優先URLを示す。公開先・転送・サイトマップと整合させ、異なる本文を一律にトップへまとめない。検索エンジンの選択を強制する指定ではない |
| `sitemap.xml` | 多数の公開ページ等で発見を助ける必要があれば用意する。掲載したい正規URLを列挙し、非公開・`noindex`・転送先でない旧URL・エラーページは含めない。なくても小規模サイトの検索掲載が不可能になるわけではない |
| OGP・SNSカード | リンクを共有する公開ページで、`og:title`、`og:type`、`og:url`、`og:image` や説明文、必要に応じたSNSカードを検討する。画像や初期HTMLを共有先が取得できるか、公開してよい内容かを確認する |
| favicon・ホーム画面アイコン | タブ・ブックマーク・ホーム画面の表示に使う。形式・URL・検証は[既存の共通方針](web-app-candidates.md#faviconホーム画面アイコンの形式とurl)に従う |
| Web App Manifest・テーマ色 | ホーム画面への追加等に必要な場合に、名前・起動URL・範囲・表示方法・アイコンを整える。既存のPWAやService Workerとの整合も確認し、検索対策だけを理由に新設しない |
| 構造化データ | 検索表示に有用な対象と実際に公開する内容がある場合に検討する。本文と一致させ、対応する検索機能の条件も確認する。追加しても検索表示は保証されない |
| `/.well-known/security.txt` | 脆弱性の連絡を受ける公開窓口を運用できる場合に検討する。実在し定期的に確認できる連絡先と期限を設定し、期限切れ前の更新を管理する |

`ads.txt` 等の広告・サービス連携用ファイルや `llms.txt` 等は、実際に使う連携・目的がある場合だけ、
提供先の仕様と運用負担を確認して判断する。必要のないファイル、架空の連絡先、意味のないメタタグを機械的に増やさない。

## クロールと検索掲載の関係

- `robots.txt` の `Disallow` はクロールを控える指示であり、他のページから発見されたURLが検索結果に現れる可能性はある。
  掲載を防ぎたい公開ページでは `noindex` を検討するが、その指示を読んでもらうには、対象クローラーがページを取得できる必要がある。
  既存のクロール制限を外すと取得される内容が変わるため、安全性と影響を確認してから変更する。
- 非公開情報は、クローラーが指示に従うことを前提にせず、認証と認可で保護する。検索結果に既に掲載された情報の除去は、
  配信の制限や削除と検索サービス側の手続き・反映状況を別に確認する。
- サイトマップに載せないこと自体は掲載禁止の指示ではない。掲載する場合は到達可能な正規URLに揃え、
  `lastmod` は実際に管理できる更新日だけを使う。不明なら省略し、ビルド日時を全ページに機械的に付けない。
  形式と件数・サイズの上限を確認し、必要な場合は分割する。

[robots.txtの説明](https://developers.google.com/search/docs/crawling-indexing/robots/intro)、
[robots metaとHTTPヘッダー](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)、
[サイトマップの作成](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)、
[canonicalの指定](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)を参照する。

## 実装・公開時の確認

1. 各ページの公開範囲と検索掲載の意図、正規オリジン、現在の設定・生成元・配信設定を確認する。
   フレームワークが自動生成するタグやファイルは重複させず、生成物を直接編集しない。
2. 生成HTMLと応答ヘッダーを、公開対象・`noindex` 対象・404・別名・プレビュー環境の代表例で確認する。
   初期HTMLと画面内遷移後が異なる場合は両方を調べ、共有先が認証やJavaScriptを実行できるとは仮定しない。
3. 必要な場合は `robots.txt`、サイトマップ、画像、manifest、`security.txt` のHTTPステータス・Content-Type・内容を確認する。
   SPAのHTMLフォールバックが200を返しただけで、目的のファイルが配信されたと判断しない。
   サイトマップはXMLを解析し、重複・非公開URL・`noindex`・転送・404・canonicalの不整合を検査する。
4. 自動テストや生成物の検査で、対象と除外条件、ヘッダー、重複しないメタ情報を確認する。
   公開後も代表URLと関連ファイルを取得し、配信された内容・キャッシュ・転送を確認する。
   認証情報や非公開ページの本文を検証ログに残さない。
5. 公開応答の確認と、検索エンジンの取得・正規URLの選択・検索掲載、SNSのプレビュー表示は別に扱う。
   Search Console等を使う場合は対象プロパティと処理結果を確認し、権限や実機がなく未確認の項目は明記する。

仕様の参照先: [Open Graph](https://ogp.me/)、[Web App Manifest](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest)、
[security.txt（RFC 9116）](https://www.rfc-editor.org/rfc/rfc9116)。
