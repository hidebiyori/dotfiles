# 会話から得た共通知見

ユーザーとの会話や検証で得た知見を、複数プロジェクトで再利用できる形にまとめる。
適用条件・判断・理由を短く残し、詳しい手順は既存の文書へ統合する。
解決済みの不具合や会話の経緯は Git の履歴で確認する。

## 参照と更新の流れ

1. 作業に関係する項目を必要時に参照し、リンク先で適用条件を確認する。
2. 作業の区切りに、今回の会話で明示された訂正・合意と、実際に検証した事実から知見を抽出する。
   関係のないリポジトリや過去の全チャットを巡回しない。
3. [採用条件](#採用条件)と[公開前確認](#公開前確認)を満たす内容を、既存の知見・手順と照合する。
4. 短い判断基準と参照先はこの文書、詳細手順は対応する `docs/`、確立した共通の行動規則は
   [`src/.codex/AGENTS.md`](../src/.codex/AGENTS.md) に反映する。プロジェクト固有の内容は各プロジェクト内で管理する。
5. dotfiles の作業指示に従い、今回の変更だけを検証・差分確認してコミット・PR にまとめる。
   作業先のリポジトリの変更とは分け、コミット・PR の件名と本文も公開前確認の対象にする。

新しい知見がなければ更新しない。重複は統合し、古くなった判断は更新・削除する。
dotfiles に安全に反映できない場合は、非公開の識別情報を含めず未反映の旨を報告する。
他の作業者の変更を上書きしたり、本来の依頼に必要な検証を省略したりしない。
ユーザーの「文書更新不要」「ローカルのみ」などの指定と、各プロジェクトの指示を優先する。

## 採用条件

- ユーザーが共通方針として明示した訂正・合意、または適用条件を確認できた検証済みの事実を対象にする。
  Codex 自身の提案や、ユーザーから異論がなかったことだけを合意の根拠にしない。
- 複数プロジェクトに適用できる条件を説明できること。一度の事情や局所的な回避策を、無条件の共通ルールにしない。
- 適用条件・判断・理由・参照先を簡潔に記す。OS・実行環境・バージョンに依存する場合は、その条件と再確認が必要になる変更を示す。
- 既存文書に同じ内容がある場合は、その文書を更新・参照する。手順の本文を重複させず、明文化済みの規則を毎回追記しない。
- 未検証の仮説や矛盾が残る内容は、共通の判断基準に採用しない。必要な調査事項は元のプロジェクト内に残す。

## 公開前確認

**dotfiles は公開リポジトリとして扱う。非公開情報は、下書き・差分・コミット・PR に入れる前に除く。**

- 非公開プロジェクトの実名・別名・所有者・リポジトリ URL・ローカルパス・内部 URL・プロジェクト ID・
  公開先・設定値・認証情報を転記しない。コマンド例、エラー出力、リンクのラベルと接続先にも同じ基準を適用する。
- 名前を伏せても、パスの一部、固有の構成、用途、複数の情報の組み合わせから対象を推測できないか確認する。
  公開する内容は、対象を特定しない条件と判断基準まで一般化する。
- 出典の文書・Issue・PR が公開可能か確認する。確認できないリンクや識別子、会話・ログの原文は載せず、
  詳しい根拠は元のプロジェクト内に残す。既存の公開文書や Git 履歴にあることだけを公開可能な根拠にしない。
- 公開可否が不明な情報や、安全に一般化できない知見は、dotfiles に転記せず各プロジェクト内に留める。
  例示が必要なら、実在の非公開情報を加工せず、対象に依存しない例を作る。
- 変更した本文・リンク・コード例と、ステージ済みの差分、コミット・PR の件名と本文を確認する。
  検索や機械的な検査では、検出した値や原文を出力せず、件数や該当箇所だけを確認する。
  文字列の検査だけで安全と判断せず、文脈から対象を推測できないかも読む。

## 再利用する判断基準

| 適用条件 | 判断と理由 | 参照先 |
| --- | --- | --- |
| 別プロジェクトの知見を公開文書へ集約するとき | 対象を特定しない条件と判断に一般化する。出典リンクからの情報露出も確認する | [公開前確認](#公開前確認) |
| Webアプリで繰り返し必要になる機能を見直すとき | favicon、ダークモード、キャッシュ優先表示などを共通対応候補として参照し、各アプリの要件・実装・検証状況を確認して採否を決める。候補の掲載だけで全リポジトリ対応済みとは扱わない | [Webアプリの共通対応候補](web-app-candidates.md) |
| 個人利用中心のサービスで保存済み画面を再表示するとき | キャッシュの読み出しと描画だけを最優先にし、それ以外は表示後へ回す。認証復元・SDK起動・権限確認等を待ってからキャッシュを出す構成にしない | [キャッシュ表示の基本方針](web-app-candidates.md#キャッシュ表示の基本方針) |
| ローカル・別 OS・CI の検証結果を報告するとき | 実行した環境と検証対象を明記する。スタブを使ったテストの成功だけで、実際のアプリ導入や UI 動作まで確認したと扱わない | [dotfiles の検証規則](../AGENTS.md)、[共通の作業品質](../src/.codex/AGENTS.md#作業品質の維持) |
| 共通指示を編集して別環境へ反映するとき | 実際に読む保存先と配置方式を確認する。コピー先には再適用が必要なため、原本の編集と有効化を分けて確認する | [配置と同期](codex.md#配置と同期) |
| 自分が所有しないサイトから続けて取得・解析するとき | 少数のURLでも同一サイトは1件ずつ取得し、応答後にsleep等で待機する。取得済み結果を再利用し、制限時は待機を増やすか停止する | [外部サイトの取得と解析](repository-maintenance.md#外部サイトの取得と解析) |
| 公開認証が不足しているように見えるとき | 導入済みのツールと既存認証で必要な操作が可能か確認する。設定の有無だけで再ログインや新規認証が必要と判断しない | [Firebase 公開認証](firebase-deploy-auth.md) |
| Firebaseの機能・公開方法を選ぶとき | 全プロジェクトでSparkを維持する。有料機能は無料で可能な代替を検討し、実装や検証を理由にプラン・課金設定を変更しない | [共通のFirebase方針](../src/.codex/AGENTS.md#firebase--github-actions-の公開認証) |
| GitHubの画面でブランチ保護の警告や案内を見たとき | 表示だけで利用可能と判断せず、公開範囲・所有者のプランと公式利用条件を確認する。プラン非対応ならPR・CI確認を作業手順で行い、強制できない制約を個別に記録する | [ブランチ保護の利用可否と運用](repository-maintenance.md#既定ブランチの保護) |
| 依存の脆弱性と期限付き例外を再評価するとき | 依存ツリーと実行環境を別に照合する。更新後の解決版と告知の撤回状態まで確認し、更新コマンドの成功や例外期限だけで判断しない | [セキュリティ確認](repository-maintenance.md#依存関係と実行環境のセキュリティ確認) |
| 新しい依存パッケージの採用を遅らせるとき | npm・uv・対応版pipには3日間の待機を設定する。端末とプロジェクトを別に確認し、既存の認証設定とlockfileを維持する。修正版も遅れるため脆弱性監査は続ける | [待機期間と例外](repository-maintenance.md#新しい依存パッケージの待機期間) |
| Linuxで既存出力の上書きを禁止する確定処理を作るとき | 存在確認後の通常のrenameでは競合時の上書きが残る。カーネル・libc・出力先の対応を確認して原子的な上書き禁止操作を使い、未対応時は上書きせず停止する | [Linux man-pages: rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html) |

項目を増やすときも、この粒度を保つ。具体的なコマンドや設定例はリンク先の手順で管理する。
