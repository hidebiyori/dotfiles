# Webアプリの共通対応候補

複数のアプリで繰り返し必要になる表示・読み込み・復帰の対応を、新規開発と既存アプリの見直しで参照する。
これは導入候補の一覧であり、全リポジトリで実装・検証済みであることを示すものではない。
対応を始めるときに各リポジトリのコード・要件・公開方式を確認し、採否と検証結果をそのプロジェクト内へ残す。

## 優先して確認する候補

| 候補 | 共通で検討する振る舞い | 採用条件・各アプリで決めること | 確認する場面 |
| --- | --- | --- | --- |
| favicon・ホーム画面アイコン | SVGを基本に、互換用ICOと高解像度・ホーム画面用PNGを用意し、各ページから参照する | [形式とURLの共通方針](#faviconホーム画面アイコンの形式とurl)を参照。既存のデザインと参照先を維持し、素材の利用権と公開方式を確認する | タブ・ブックマーク・ホーム画面、小さいサイズ、明暗の背景、HTMLの参照先、HTTP応答・MIME・配信内容、更新時のキャッシュ |
| ダークモード | OSの配色設定に追従し、背景・文字・罫線・リンク・入力欄・フォーカス表示を配色変数で揃える。ブラウザーの操作部品も`color-scheme`と整合させる | 手動切替と設定の保存は必要な場合に追加。既存の配色・紙面・画像を保ち、画面全体の強制反転は避ける | 初回表示、OS設定の変更、入力・エラー・選択・無効状態、明暗それぞれの読みやすさ |
| キャッシュ優先表示 | 個人利用中心のサービスでは、保存済みの画面を他の処理より最優先で表示する。認証復元・SDK起動・権限確認・同期等を表示の前提にしない。ページ遷移でも本文・状態・購読を共有する | [キャッシュ表示の基本方針](#キャッシュ表示の基本方針)に従う。公開範囲、前回の利用者・保存先の区別、期限、保存容量、明示的な更新と削除を各アプリで定める | アプリのJavaScript・SDK・認証・通信を遅らせても保存画面が先に見えること、再訪・ページ往復、保存領域の無効・満杯・破損 |
| キャッシュの更新と破棄 | 通常は変更分だけを同期し、明示更新では最新の内容を取得する。ログアウト・利用者変更・権限失効で必要な保存内容を消し、古い応答による復活を防ぐ | 更新通知・版番号・取得単位はデータ構造に合わせる。権限を確認できない間の表示と、取消しが端末へ反映される条件を明示する | 同じ版、変更・削除、更新中の離脱、ログアウト、利用者切替、権限取消し、複数タブ |
| オフライン・通信失敗からの復帰 | 読める保存内容や入力途中の内容を保ち、同期状況と再試行方法を示す。キャッシュがない場合も空白や無限の待機にしない | 閲覧可能な範囲、未保存の扱い、オンライン復帰時の再取得を決める。書き込みの自動再送は重複・競合への対応を確認してから採用する | 通信切断、タイムアウト、再接続、タブ復帰、ブラウザー再起動 |
| 公開後の更新と復帰 | ハッシュ付き静的ファイルとHTMLのキャッシュ方針を分け、古い画面から新しい公開版へ復帰できるようにする | Service WorkerやPWAは必要なアプリだけで使う。非公開本文・認証情報を公開画面用キャッシュへ入れない。公開方式とオフライン時の制約を確認する | 旧HTML、遅延した配信ファイル、更新前後のタブ、再起動、オフラインからのオンライン復帰 |
| エラーと再試行 | 利用者が次に取れる行動を日本語で示す。通信・権限・入力・上限超過などを区別し、再試行ボタンと実行中の状態を揃える | SDKの例外本文・応答本文・内部識別子・認証情報をそのまま画面やログへ出さない。取消しは失敗と分ける | オフライン、権限不足、入力不備、待機時間超過、連打、ポップアップの取消し・ブロック |
| 表示位置の安定 | 読み込み・通知・更新で本文や操作位置を意図せず動かさない。通知は内容の重要度に応じて邪魔にならない位置・持続時間を選ぶ | 必要な状態やエラーは見逃さないようにし、読み上げ・操作・狭い画面や拡大時の重なりも考慮する | 初期表示と復元、通信状態の変化、通知の出現・消失、狭い幅と拡大表示 |
| フォント | 通常画面は共通のサンセリフ体指定を候補にし、用途に応じて選ぶ | [フォント指定の共通方針](#フォント指定の共通方針)を参照。既存画面にも採用を検討し、一覧性・レイアウトや意図した等幅・書体は保つ。文字サイズの変更は別に判断する | 対象端末での日本語・英数字、表の列幅・折り返し、入力欄、拡大表示、フォントを取得できない場合 |
| スマートフォン表示と入力 | 長い見出し・URL・表を読めるようにし、入力欄・操作領域・画面端の余白を確保する。既存の画面構成と文字サイズの要件を保つ | 対象の画面幅、固定ヘッダ・フッタ、safe area、ソフトキーボードの影響は画面ごとに判断する。iOS Safariでテキスト入力欄のフォーカス時にページ拡大が起きる場合は、その欄の計算済み`font-size`を16px以上にする。行高・余白を調整して欄の寸法を保ち、ユーザーによる拡大操作は制限しない | 狭い幅、横向き、長文、拡大表示、キーボード表示中の操作 |
| アクセシビリティ | 意味に合う見出し・ラベル・ボタンを使い、キーボードで操作できるようにする。フォーカス、状態通知、動きを減らす設定を考慮する | ダイアログ・ページ内遷移・非同期更新ではフォーカスの移動先と読み上げの必要性を決める | Tab・Enter・Escape、フォーカスの可視性、読み上げ用の名前、処理中・完了・失敗の通知 |
| 案内・アカウント | サービス紹介・利用規約・プライバシー・問い合わせへの導線とアカウント操作を点検する | ページの構成・ログアウトの場所・検索エンジンへの公開可否は用途と共有範囲に合わせる。不要な定型ページを機械的に増やさない | 案内ページからの復帰、未ログイン・ログイン中、保存内容の説明、メタ情報の配信 |

## フォント指定の共通方針

通常画面では共通の書体指定を使うことを検討し、既存画面にも、表示と利用目的に合えば取り入れる。
表の一覧性、文字の配置、既存デザインを保つ必要があれば、現在の指定を維持する。
共通指定でも各端末の表示が同一になるとは限らないため、選び方と確認方法も揃える。
判断の背景と代替案は [ADR](adr/0003-font-selection.md) に記す。

通常の本文・操作画面では、端末にある書体を使う `sans-serif` を共通の候補にする。
画面の目的や対象環境に合わせて別の書体を選んでよい。日本語の文書には適切な言語を指定する。
文字サイズはサイト間でも共通の目安を設けられるか検討する。各サイトの現在のサイズと対象端末での読みやすさ・表示領域を比較し、
共通の値で支障があるサイトは個別に決める。通常の本文・メニュー・操作の文字は、少なくともサイト内で共通の基準に揃える。
必要に応じて画面幅ごとに基準を設け、入力欄や一覧などに理由のある例外を設ける。行高・太さも用途に合わせる。
既存画面の書体を揃える場合は現在の文字サイズを維持し、サイト間・サイト内のサイズ統一を含め、変更が必要なら影響を確認して別に判断する。

```css
body {
  font-family: sans-serif;
}
```

- 指定書体が使えない場合に備え、書体名を列挙するときも最後に用途に合う `sans-serif`、`serif`、`monospace` 等を置く。
  [CSS Fontsの仕様](https://www.w3.org/TR/css-fonts-3/#font-family-prop)では文字ごとに利用可能な書体が選ばれるため、
  同じ指定でもOS・ブラウザー・言語・文字によって見た目や字幅は変わり得る。
- コード、空白で位置を揃えた文章、表など、等幅や特定の字形が意味・一覧性に必要な箇所は、その指定と空白・改行を保つ。
  `monospace` の指定だけで日本語を含むすべての文字が意図した幅に揃うとは限らないため、実際の文字と対象環境で確認する。
  数字だけを揃えたい場合は `font-variant-numeric: tabular-nums` も候補にし、使用書体での効果を確認する。
- 入力欄やボタンを本文と揃える場合も、コード入力などの個別指定を守る。iOS Safariの入力時の拡大対策は
  [スマートフォン表示と入力](#優先して確認する候補)に従い、書体の変更と文字サイズの変更を区別する。
- ダウンロードするフォントは、端末の書体では満たせない目的があるときに検討する。利用条件、転送量、取得失敗・オフライン時の代替、
  表示開始とフォント切替による位置の変化を確認する。表示をフォントの取得完了待ちにしない。

フォントを変更するときは、変更前後の代表画面で、対象のPC・スマートフォンの幅とブラウザー、通常表示と拡大表示を確認する。
日本語・英数字・記号、長い項目、表の列幅・折り返し・見える情報量、ボタン・入力欄のはみ出しや欠けを比較する。
表に横スクロールが必要でも内容と操作を利用できるようにし、拡大操作を制限しない。
[文字の拡大](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)と
[リフロー](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)も参照し、確認できなかった端末や書体は未確認とする。

## favicon・ホーム画面アイコンの形式とURL

サイトのルートを管理できる場合、ブラウザー向けはSVGを基本とし、用途ごとに次の形式とURLを使う。
各形式は同じサイトだと分かるデザインにする。ブラウザーや検索サービスが選ぶ形式は異なるため、SVGだけにはしない。

| URL | 形式・サイズ | 用途 |
| --- | --- | --- |
| `/icon.svg` | SVG | 通常のアイコン。HTMLで `rel="icon"` と `type="image/svg+xml"` を指定する |
| `/favicon.ico` | ICO、16・32・48pxを格納 | SVGを使えない環境や、このURLを直接参照する利用先向け。HTMLでも `rel="icon"` を指定する |
| `/apple-icon.png` | PNG、180×180px | iPhoneなどのホーム画面向け。HTMLで `rel="apple-touch-icon"` を指定する |
| `/icon.png` | PNG、192×192px | 高解像度のアイコン向け。HTMLで `rel="icon"` とサイズを指定する |

`/icon.svg` は明示的に指定する。自動取得側が宣言のない `/favicon.svg` を推測して問い合わせる必要はない。
Google検索の[対応形式とサイズ](https://developers.google.com/search/docs/appearance/favicon-in-search)にはSVGが含まれないため、
検索表示にはICOやPNGを使う。指定は検索結果への表示を保証しない。
複数の `rel="icon"` を宣言しても、実際の選択はブラウザーやサービスによって異なる。

ホーム画面用のPNGは、ファイル名の自動探索に依存せず `rel="apple-touch-icon"` で指定する。
Next.js App Routerでは `app/favicon.ico`、`app/icon.svg`、`app/apple-icon.png` を配置すると
[link要素が自動生成される](https://nextjs.org/docs/app/api-reference/file-conventions/metadata/app-icons)ため、同じ指定を重複追加しない。
生成された参照先にはキャッシュ用のクエリが付く場合がある。ファイル名だけでなく、出力されたHTMLのURLを確認する。
PWAを採用する場合は、別途manifestに192・512pxのPNGと、必要に応じてmaskable用のアイコンを指定する。

変更時は次を確認する。

- 既存のモチーフ・色・利用権を保つ。SVGの元画像がなく、変換で見た目を保てない場合は、既存画像を維持して個別に判断する。
- 既存URLへの外部参照、Service Workerやキャッシュを確認し、必要な旧URLは残す。サブパスで公開しルートを共有する場合は、他サイトのアイコンを上書きせず公開方式に合わせる。
- 各ページの生成HTMLで `rel`・URL・形式・サイズを確認し、各URLがHTTP成功・正しいMIME・実際の画像を返すことを確認する。SPAのHTMLへの書き換えを画像の成功と扱わない。
- 16・32pxの視認性、明暗両方の背景、ホーム画面、更新後のキャッシュを確認する。公開応答の確認と実機での表示確認は区別する。

## 必要な場合に検討する候補

以下は、必要性と実装・検証・保守の負担が見合う場合に検討する任意の候補とする。
全アプリの必須対応や着手予定とはせず、現時点では見送る判断も含める。

| 候補 | 検討する価値がある場面 | 採否の判断材料 | 採用時に確認すること |
| --- | --- | --- | --- |
| オフライン起動・閲覧 | 通信が不安定な場面でも、保存済みの内容をブラウザーで開き直して閲覧・検索する価値がある | 利用頻度・既存キャッシュ・実装量に加え、CI・公開版更新・対象ブラウザーの検証と保守の負担を比べる。負担が上回る場合は見送る | [共通の検討事項](web-app-offline.md)を参照し、準備完了、保存範囲、権限、再接続、公開版の切替を確認する。書き込み・再送は別に検討する |

## キャッシュ表示の基本方針

個人利用中心のサービスでは、キャッシュを読む・描画するために必要な最小限の処理だけで、保存済みの画面を最初に表示する。
「認証が終わったらキャッシュを使う」「SDKやデータ全体の検証を待ってからキャッシュを出す」構成にしない。
表示前に待機時間を設けず、それ以外の処理は実際の表示後へ回すことを基本にする。

- 初期HTMLから使える軽量な表示コピー等を用意し、アプリの起動・認証復元・SDKの読み込みを表示の前提にしない。
  キャッシュがある間は、裏の処理を始めるために待機画面へ差し替えない。
- 権限・更新の確認、同期、移行、詳細な検証、保存の整備は表示後に行う。新しいデータの取得ではサーバーの権限確認を維持する。
- ログアウト・利用者の変更・権限失効が判明した場合は該当する本文と保存内容を消し、古い応答で復活させない。
  前回の利用者のコピーを認証前に表示する動作と、オフライン中の失効が反映される条件を各アプリ内で説明する。
- キャッシュなしの初回、明示更新、異なる保存先・期限切れ・破損の扱いを分ける。
  JavaScript・認証・通信を意図的に止めるか遅らせ、保存済み画面の表示がそれらを待たないことを確認する。

## 共通化の進め方

1. 対応する画面・利用者・データを確認し、上の候補の採否と未対応の範囲を決める。
   リポジトリの指示と利用者の要件を優先し、候補という理由だけで機能を追加しない。
2. 共通にする振る舞いと、アプリ固有の値・画面構成・権限を分ける。
   同じ設計を再利用できても、データ取得や認証を一律に同じ実装へ寄せる必要はない。
3. 差分に合うテストを追加し、まず導入済みのツールで軽量に確認する。
   表示・ブラウザー固有の問題が残る場合は、必要な範囲で画面を確認する。
4. 各リポジトリで検証・コミット・PR・CIを経て反映する。公開後の確認と実機での操作確認を区別する。
   未確認の項目を、実装済みであることだけで完了にしない。
5. 複数の利用先で共通部分を確認してから、必要なら設定・補助処理・検証を共有する。
   dotfilesの更新から各アプリへ自動適用しない。

オフライン起動を検討する場合の採否・設計・利用案内・検証は [共通の検討事項](web-app-offline.md) を参照する。
任意の候補とし、閲覧と書き込みを分けて判断する理由は [ADR](adr/0002-offline-scope.md) に記す。

ビルド・lint・型検査・ディレクトリ構成は[Next.jsの共通設定](project-presets.md)、
公開・依存更新・CIは[リポジトリ共通の保守](repository-maintenance.md)を参照する。
知見の公開可否は[公開前確認](learnings.md#公開前確認)に従い、非公開の実装例や対象を特定できる出典を転記しない。
