# Webアプリのオフライン対応を検討する

オフライン起動・閲覧は、必要性と実装・検証・保守の負担が見合う場合に検討する任意の候補とする。
全アプリの必須要件や着手予定とはせず、未対応のまま運用する判断も含める。
[共通対応候補](web-app-candidates.md#必要な場合に検討する候補)から採否を検討するときと、採用を決めた後の保存範囲・更新・検証を整理するときに参照する。
具体的な実装・保存期限・対応環境は各プロジェクトの文書で管理する。
この文書の追加で、全アプリへの導入や動作確認が済んだことにはしない。

## 導入を判断する

- 利用価値: 通信がない場面で使う頻度と、保存済み内容を開けることで解決する困りごとを確認する。
- 実装の負担: 既存キャッシュを使える範囲、起動・画面遷移に必要な追加処理、通信が必要な機能との分離を確認する。
- 検証・保守の負担: CIでの再現性、対象ブラウザー・実機の確認、新旧の公開版の切替、更新失敗時の復旧を維持できるか確認する。

利用価値に比べて負担が大きければ、導入を見送る、通常の通信エラーからの復帰だけを改善する、対象画面を絞って試す選択肢を残す。
既存のキャッシュ、利用場面、検証環境が変わったときに採否を見直せる。以下は、検討を進める場合・採用を決めた場合の確認事項である。
CIの実行時間と検証範囲の判断は [リポジトリ共通の保守](repository-maintenance.md#ci-の実行時間と検証範囲) を参照する。

## 対応範囲を決める

| 範囲 | 目標と追加で決めること |
| --- | --- |
| 表示中の通信切断からの復帰 | 読める本文と入力を保ち、通信失敗と再試行を案内する。これだけでは通信なしの再起動を保証しない |
| オフライン起動・閲覧 | オンラインで準備した端末で、ブラウザーを終了して起動し直しても、保存済みの画面・本文を開ける。対象の検索・画面遷移も含めて必要なファイルを揃える |
| オフライン書き込み・同期 | 未送信変更の保存、再送の重複防止、他端末との競合、権限失効、失敗時の回復を別途設計する。閲覧対応だけを根拠に有効化しない |

まず必要な画面・操作と、通信が必要な操作を棚卸しする。閲覧中心のアプリでは、保存済み内容の起動・検索・全文表示から検討する。
初回ログイン、未保存データの取得、外部サイト、クラウド側だけで行う処理は、通信なしで使える範囲へ含めない。
端末で代替処理を動かす案は、必要な実行環境・容量・性能を確認する別の設計判断とする。

Service WorkerやPWAは目的に合う場合だけ選ぶ。ホーム画面への追加と、起動用ファイル・本文の保存完了は別に確認する。
任意の候補とし、閲覧と書き込みを分ける理由は [ADR](adr/0002-offline-scope.md) を参照する。

## 保存と起動

| 保存対象 | 共通の扱い |
| --- | --- |
| 公開画面と静的ファイル | 対象のHTML・JavaScript・CSS・画像・フォント・画面遷移用データを列挙する。公開本文・検索データを含める場合も、公開対象だと確認したものに限る |
| 非公開本文・検索データ | 利用者・保存先を区別した端末コピーとして管理し、公開ビルドや公開画面用キャッシュへ混ぜない。表示用コピーに認証トークンを含めない |
| 認証・データ取得・外部通信 | 汎用の画面キャッシュの対象外にする。新しいデータの取得ではサーバーの認証・権限確認を維持する |
| 公開版の確認情報 | 古い画面キャッシュだけで最新版と判定しない。通信できない場合は確認できていないことを区別する |

- 本文のキャッシュだけで起動可能と判断せず、対象機能で必要になる遅延読み込み・画面遷移も保存範囲へ含める。
- 保存済み画面を出す順序は [キャッシュ表示の基本方針](web-app-candidates.md#キャッシュ表示の基本方針) に従う。
  追加の保存処理・SDK・認証・更新確認のために、表示を待たせたり待機画面へ戻したりしない。
- 準備中・利用できる範囲・準備失敗を利用者が判断できるようにする。画面と本文の必要な保存が揃う前に、準備完了と案内しない。
- 保存期限・容量上限・破損時の扱いをアプリで決める。保存領域が使えない・満杯・消去された場合も、通常のオンライン利用と復旧方法を残す。
  ブラウザーや利用者による削除があり得るため、アプリの保存期限まで必ず残るとは保証しない。[保存容量と削除の条件](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- Service Workerを採用する場合は、配信先のHTTPS、スコープ、MIME、配信ヘッダーと対象ブラウザーを確認する。
  登録・有効化・保存の状態を区別する。[Service Workerの基本](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers)

## 切断と再接続

切断中は保存済みの本文・検索・閲覧位置を保ち、できない操作と再接続後にできることを示す。
通知の出現・消失で本文や操作を動かさず、重要な状態を読み取れる形にする。[表示位置の方針](adr/0001-stable-display.md)

- オフライン書き込みを採用していない操作は無効にし、未保存の変更を保存済みと表示したり、後から黙って送信したりしない。
- 更新・再試行で、オフライン中に唯一の閲覧可能なコピーを先に消さない。キャッシュがなければ、オンラインで準備する手順を案内する。
- 再接続では保存済み表示を維持しながら利用者・権限・更新を確認し、必要なデータだけを同期する。確認前に書き込みを有効にしない。
  ブラウザーの接続状態の表示だけで、サーバーへの接続や権限が確認できたと判断しない。
- ログアウト・利用者変更・権限失効が判明した場合は対象の本文と端末コピーを消し、別タブへ反映する。
  古い応答や保存処理で復活させない。切断中の権限取消しを確認できる時点も利用案内に明記する。

## 公開版の更新

1. 起動用ファイルを版ごとに揃え、取得途中の失敗や新旧ファイルの混在を検出する。準備に失敗した版へ切り替えず、利用できる旧版を残す。
2. 新しい画面の適用と、本文データの再取得を分ける。画面を更新するためにログアウトや非公開データの削除を通常の手順にしない。
3. 開いているタブ・入力・閲覧位置への影響を確認する。即時切替を採用する場合も利用者が選べるようにし、対象のタブが安全に切り替われることを確認する。
   旧版や応答のないタブがある場合は強制適用せず、現在の版を保ってタブ終了・次回起動へ延期する。
4. 旧画面が必要とする資産とキャッシュの削除時期を決める。更新後のオンライン・オフライン双方の起動と、失敗時の回復を確認する。

Service Workerの待機と有効化の仕組みは [更新の説明](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers#updating_your_service_worker) を参照する。
具体的な更新操作・互換性の確認方法・旧版からの移行手順は各アプリの運用文書に残す。

## 検証と各アプリへの反映

| 場面 | 確認すること |
| --- | --- |
| 準備後の起動 | 接続中に準備し、通信を切って実際にブラウザーを終了・起動し直す。初期表示、対象画面への移動、検索、全文が利用できる |
| 未保存・保存失敗 | 初回・期限切れ・容量不足・破損・保存領域の無効化を区別し、無限待機や空白にせず準備・復旧の案内を出す |
| 切断・再接続 | 表示と入力を維持し、対象外の操作を送信しない。復帰後は権限を再確認し、同期失敗を保存成功と表示しない |
| 利用者・権限 | ログアウト、別利用者、権限取消し、別タブ、遅い応答でも、無効にしたコピーが復活しない |
| 公開版の切替 | 旧HTML、遅延資産、準備途中の切断、新旧タブ・未応答タブ、切替失敗、再起動から安全に復帰できる |
| 公開物と表示 | 非公開データ・認証情報が公開ビルドや公開画面用キャッシュに入らない。対象ファイルの版・ハッシュ・MIME・配信ヘッダーと、通知による本文の移動や遮りを確認する |

まず単体テスト・スタブ・成果物検査を使い、Service Workerやブラウザー再起動など実環境が必要な項目は、導入済みのブラウザーやCIで順番に検証する。
合成データ・エミュレーター・CIの成功と、公開先・実アカウント・対象のAndroid/iOS実機での確認を区別する。
対象環境、確認できた範囲、未確認事項と再確認条件を各アプリの開発・運用文書へ記す。完了した試行や過去のテスト件数はGit・PRで参照する。

実装は各リポジトリで検証・コミット・PR・CI・公開確認を経て反映する。
保存期限・認証・データ取得方式を一律に揃えず、複数の利用先で共通部分を確認してから補助処理の共有を検討する。
