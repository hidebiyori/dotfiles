# ドキュメントの管理方針

ドキュメントは、現在の仕様・編集場所・操作手順・制約を確認するための正本にする。
変更の経緯や完了した対応記録はGit・PRで参照する。構成や手順を変更したら、該当する説明そのものを更新する。

## 文書の役割

| 文書 | 読み手が確認すること |
| --- | --- |
| `README.md` | 何のプロジェクトか、最短の始め方、日常のコマンド、詳細文書への入口 |
| `docs/architecture.md` | 現在の構成、編集元と生成物、データの流れ、外部サービスとの境界 |
| `docs/development.md` | 開発環境、起動、変更内容に応じた検証、対応OSと制約 |
| `docs/operations.md` | 公開・保守・復旧の手順、必要な権限、現在の未実施事項と再確認条件 |
| 分野別の文書 | 本文の編集、認証、バックアップ等の詳細。正本を決め、ほかからリンクする |

小さいプロジェクトはREADMEだけでもよい。長い公開手順は `deployment.md`、複数ツールの説明は
`tools/<tool>/README.md` 等へ分けられる。既存の適切な名前やリンクを、名前の統一だけのために変更しない。
空の文書・見出しや、実装していない機能の説明は追加しない。

## 内容の書き方

- 現在できること・編集する場所・必要な手順を先に書く。対象や前提が変われば本文を置き換える。
- 対応済み事項の時系列、過去のテスト件数、会話の引用、試しただけのコマンドを蓄積しない。
- 現在の設計を支える理由、継続中の例外、非対応環境、復旧の制約は残す。
- 実装済み・公開済み・実機で確認済みを区別する。未確認を完了として書かない。
- 未実施事項は、何を確認するか・何が必要か・どんな変更時に再確認するかを示す。
  期限や確認日は、継続中の例外・外部条件の判断に必要な場合だけ付ける。
- 計画は確定した要件と未決の案を分け、実装済み事項を「これから作ること」に残さない。
- READMEと詳細文書に同じ手順を複製しない。READMEの一覧から現在の正本へ到達できるようにする。

過去の文書を整理する際は、未解決事項・判断理由・利用者が必要とする資料を先に引き継ぐ。
不明な状態は未確認として残し、過去の記録だけから完了と推測しない。
アプリの原本データや利用者のノート・作品等は、開発上の対応記録とは別に扱う。

## 雛形と各プロジェクトへの反映

雛形は [`src/project-presets/documentation/`](../src/project-presets/documentation/) に置く。
READMEと構成・開発・運用の見出しを、新規プロジェクトや既存文書の見直しに使う。
既存文書を一括で上書きせず、実際の構成・コマンド・未実施事項を確認して必要な部分を取り込む。

共通方針と雛形はdotfiles、現在の仕様と具体的な設定・手順は各プロジェクトでGit管理する。
雛形を利用した後の文書は各プロジェクトが正本であり、ビルドや閲覧時にdotfilesを必要としない。
雛形の更新を各プロジェクトへ自動反映しない。
公開する共通文書には、非公開プロジェクトの名前・パス・URL・識別情報を含めない。

## 更新時の確認

1. 実装・設定・現在の検証コマンドと説明が一致しているか確認する。
2. 未実施事項と判断理由の取りこぼし、重複する正本、古い時系列の追記を確認する。
3. READMEやほかの文書からの案内を更新し、変更前の参照先を検索する。
4. [Markdownの相対リンク検証](repository-maintenance.md#markdown-の相対リンク検証)と
   `git diff --check` を実行する。見出しアンカーは相対リンク検証の対象外なので別途確認する。
5. 秘密情報・公開範囲・ステージ済み差分を確認し、各プロジェクトの手順でコミット・PR・CIへ進める。
