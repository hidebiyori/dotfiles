# 作業完了時のコミット・PR・マージ

- Git 管理されたリポジトリで変更を伴う依頼では、それぞれの対応が一段落した時点で必要な検証と差分確認を行い、その対応をコミットする。複数の対応を含む場合も、全対応の完了までコミットを先送りしない。通常は追加の確認を求めず実行する。
- ユーザーがコミット不要・ローカルのみ・レビュー待ち・マージ不要などを指定した場合や、プロジェクト固有の指示がある場合は、その指示を優先する。
- 作業開始時に Git の状態を確認する。既存の変更や他の作業者の変更を巻き込まず、今回の変更だけをファイルまたはハンク単位でステージする。安全に分離できない場合はコミットせず、理由を報告する。
- コミット前にステージ済み差分を確認し、秘密情報や不要な生成物が含まれていないことを確認する。
- コミットは意味のある変更単位にまとめ、リポジトリの慣例に沿って変更内容が分かるメッセージを付ける。
- コミット時は `japanese-commit` スキル（`~/.agents/skills/japanese-commit/SKILL.md`）を利用し、日本語の件名と複数行の本文に変更内容・理由・検証結果を書く。ユーザーやプロジェクト固有の言語・形式の指定を優先する。
- 必要な検証に失敗した場合は修正する。解決できない場合は未完了として報告し、完了した変更としてコミットしない。検証できない場合は理由を明記し、成功したと扱わない。
- GitHub などで PR を利用できるリポジトリでは、依頼された一通りの対応が完了し、必要な検証と差分確認を終えた後、各対応のコミットを作業ブランチへ push し、PR を作成する。原則として必須 CI の成功を確認して既定のブランチへマージするところまで、追加の確認を求めず進める。既存の対象 PR がある場合はそれを更新する。
- 必須 CI の失敗、競合、権限不足、ブランチ保護などでマージできない場合は、原因を確認し、安全に解消できるものは対応する。必須チェックや保護を回避する強制マージは行わず、未完了の内容と理由を報告する。PR を利用できない環境では、その制約を報告する。
- マージで CI や公開が起動する場合は、実行結果と必要な公開確認まで追う。未確認の公開を完了したと報告しない。
- 変更がない場合は空コミット・空 PR を作らない。明示的な依頼なしに既存コミットの amend、履歴の書き換えをしない。
- 最終報告には変更概要、検証結果、コミットの短いハッシュ、PR のリンクとマージ状況を含める。コミット・PR 作成・マージ・公開確認を完了できなかった場合は理由を伝える。

# 秘密情報を出力・再掲しない

- トークン、API キー、パスワード、Cookie、認証ヘッダーなどの値を、チャット、ツール出力、ログ、差分、コミットメッセージへ出力しない。確認には値の有無・設定名・認証情報を除いた接続先など、必要最小限の情報を使う。
- Git の接続先 URL や設定ファイルには認証情報が含まれる可能性がある。`git remote -v`、設定全体の表示、環境変数の一括表示などをそのまま実行せず、必要な項目だけを取り出し、秘密情報を除いてから出力する。出力後に伏せる方法では防止にならない。
- URL はユーザー名・パスワードだけでなく、クエリ・フラグメントに含まれる認証情報も確認する。通常の接続先確認では認証情報を除いたホスト名・パスだけを表示する。ユーザー操作に必要な一時接続 URL はそのユーザーへ必要な範囲で提示し、Git 管理の文書やログへ転記しない。
- 誤って秘密情報を表示した場合、その値や一部を報告・説明・引用で再掲しない。何の情報がどの出力に含まれたかと、失効・再発行など必要な対応だけを伝える。実施していない失効・削除を完了したと報告しない。

# 通信量を抑える

- 通信速度が遅いため、ローカルのファイル・導入済みツール・キャッシュを優先し、不要なネットワーク通信や同じ情報の再取得を避ける。
- `npm ci`、依存ディレクトリの削除を伴う再インストール、ランタイムや大型ツールのダウンロードは、ユーザーが明示的に依頼・許可した場合のみ行う。検証や脆弱性対応の一般的な依頼だけで、これらが許可されたとは扱わない。
- 依存更新が必要な依頼では、対象を絞って更新し、導入済みの依存関係で検証する。再現性確認だけを目的とした再インストールを繰り返さない。
- 必要な通信は対象・回数を最小限にする。通信や再インストールを省いたために確認できない項目は、その制約を明記し、検証成功と扱わない。
- スキルがクリーンインストールなどを推奨していても、この通信量に関するユーザー方針を優先する。

# Firebase / GitHub Actions の公開認証

- 公開用の GitHub Secret がないことだけで認証設定をユーザーへ依頼せず、既存の別プロジェクトの workflow、過去チャット、導入済みの `gcloud` とローカル ADC を先に確認する。共通手順は `~/git/dotfiles/docs/firebase-deploy-auth.md` を参照する。
- `gcloud` の通常のアクティブアカウントがなくても、既存の ADC を `CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE` に指定して読み取りが通る場合がある。認証ファイルの本文・トークンを表示せず、対象プロジェクトの読み取りと必要な管理権限を確認する。再ログインやツールの再導入は必要性を確認してから行う。
- 新しい GitHub Actions の公開認証は、長期サービスアカウント鍵より Workload Identity Federation / OIDC を優先する。対象リポジトリと所有者の数値 ID、公開ブランチ、公開イベントを制限し、公開専用サービスアカウントに必要な権限だけを与える。
- 同じ Firebase プロジェクトに複数 Hosting サイトがある場合は、デプロイ先の Hosting target を明示する。公開は検証成功後だけに実行し、マージ・認証設定・デプロイ成功・本番反映を区別して確認する。

# スキル用 Python

- スキル付属の Python スクリプト（例: `skill-creator` の `quick_validate.py`）には、導入済みの `~/.local/share/codex-skill-python/bin/python` を優先する。PyYAML を含む共通の仮想環境で、作業リポジトリの依存関係とは分離している。
- 環境がない場合は `~/git/dotfiles/bin/setup-skill-python.sh` と README の手順を参照する。通常の検証では再作成・再インストールをせず、プロジェクト固有の Python 環境はそのリポジトリの指示を優先する。

# Chrome / Playwright の接続

- Chromebook の ChromeOS 側の Chrome を調査するとき、Linux 側で `Playwright Extension not found` が出ても、拡張機能が未導入・接続不能と断定しない。導入済みの Playwright MCP と接続リンクを使う方法を確認する。
- 共通手順は `~/git/dotfiles/docs/playwright-extension.md` を参照する。通常の接続が使える場合はその接続を再利用し、不要な再インストール・ブラウザーのダウンロードは行わない。
- 接続を新しく作る場合はチャットごとのクライアントを用意し、ユーザーに対象タブを選択してもらう。他のチャットで使用中の接続・プロセスを終了したり、調査中のタブを奪ったりしない。
- 接続 URL はクライアント起動ごとに生成する。過去の URL・ポート・接続 ID を流用せず、Git 管理のファイルには保存しない。
- 接続待ちと接続成功を区別し、接続後は実際の URL・タイトルを確認してから対象サイトを操作する。リロードや移動の必要性と作業中の入力への影響を確認する。

# Crostini のメモリ・CPU負荷を抑える

Codex の作業品質を維持しながら、不要なブラウザ起動やプロセスの常駐によるメモリ・CPU負荷を削減する。以下をすべてのプロジェクトでの共通運用とする。

## ブラウザの自動起動を原則禁止

- Chrome、Chromium などの GUI ブラウザを通常の作業で自動起動しない。
- `xdg-open`、`open`、`sensible-browser` などによるブラウザの自動表示を避ける。
- Playwright、Puppeteer などによるブラウザ操作やスクリーンショット取得も、通常の動作確認では原則使用しない。
- Web ページの内容確認には、可能な限り `curl` などの軽量な CLI ツールを利用する。

## Playwright MCP は必要時だけ起動する

- Playwright MCP は通常、共通設定 `~/.codex/config.toml` の既存の `[mcp_servers.playwright]` で `enabled = false` にし、チャット開始時の自動起動を無効にする。`CODEX_HOME` を指定している場合はその設定を確認する。実行パス・引数は残し、ツールの再インストールは行わない。
- `AGENTS.md` の指示だけでは MCP の自動起動は止まらない。設定が有効な環境で変更が必要な場合は、他の進行中チャットへの影響を確認する。設定の反映を理由にアプリを再起動したり、既存の接続を終了したりしない。
- 下記の例外に該当するブラウザ検証では、`~/git/dotfiles/docs/playwright-extension.md` に従って、このチャット専用のクライアントを必要な時点で起動する。既にこのチャットの接続があれば再利用し、検証のためだけに共通設定を常時有効へ戻さない。
- 検証終了後は自分で起動したクライアントの標準入力を閉じて正常終了を待ち、必要ならそのプロセスだけに `SIGTERM` を送る。終了したことを確認し、接続維持を依頼されているものや他のチャットの接続は残す。
- `cua_node` にはブラウザ以外の Node REPL、コードレビュー、アプリ操作用 MCP も含まれる。名前だけで停止・無効化せず、使用中か不明なプロセスや Codex 本体・renderer を終了しない。

## Playwright などの例外的な利用

以下の場合は、必要に応じてブラウザを起動してよい。

- 原因不明のエラーがあり、ブラウザ上での再現・調査が必要な場合。
- JavaScript の実行時エラーやブラウザ固有の問題を調査する場合。
- UI の表示崩れ、操作不具合など、実際の画面確認が必要な場合。
- CLI による検証では問題を特定できない場合。
- ユーザーからブラウザを利用した検証を明示的に依頼された場合。

例外的に使用する際も、以下を守る。

- まず軽量な方法で検証し、必要になった時点でブラウザを利用する。
- 原則としてブラウザは 1 インスタンスとし、同時実行も最小限にする。
- ヘッドレスモードを優先する。ただし、ヘッドレスでは再現しない問題は GUI を使用してよい。
- 調査終了後は、この作業で起動したブラウザと関連プロセスを確実に終了し、終了したことを確認する。ユーザーや他のチャットが使用中のブラウザ・接続・プロセスは終了しない。
- 不要なスクリーンショットやトレースファイルを蓄積しない。

## メモリ・CPU負荷の抑制

- 不要な並列処理を避ける。
- ビルド、テスト、型チェックなどの重量級処理を可能な限り同時実行しない。
- Next.js などの開発サーバーや watch プロセスを不要に常駐させない。
- 作業のために起動した一時的なプロセスは、終了時に停止し、停止したことを確認する。
- 大量のファイルを対象とした処理では、必要に応じて対象範囲を絞る。
- メモリ不足が疑われる場合は、`free`、`ps` などの軽量な CLI ツールで実行中のプロセスやメモリ使用量を確認し、並列数を減らすなど負荷を抑える。

## 作業品質の維持

- リソース削減を理由に、必要なエラー調査や検証を省略しない。
- lint、型チェック、ユニットテストなどの軽量な検証は通常どおり実施する。負荷が高い場合は順番に実行する。
- ブラウザが必要な場合は適切に利用し、問題の再現性や原因特定を優先する。
- 検証方法を変更したことで確認できない項目が生じた場合は、その旨を報告し、検証成功と扱わない。
